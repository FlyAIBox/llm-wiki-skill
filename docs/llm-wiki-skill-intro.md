# LLM Wiki：一个让 AI Agent 帮你积累知识的技能

## 零、它解决什么问题？

你让 AI Agent 帮你调研、分析、写代码、做判断。每次对话都产出了大量有价值的东西：发现了新的信息源、推翻了一个旧判断、找到了两个概念之间的关系、确认了一个方案比其他方案好。

但下次换一个 Agent（或者同一个 Agent 开了新对话），这些东西就全丢了。Agent 不记得昨天的结论，重复问一样的问题、犯一样的错。

**LLM Wiki 就是解决这个的。**

它给你的 Agent 一个外部的、持久的知识库，在 Markdown 文件里存着，Agent 每次干活之前先去读一读"我们以前是怎么判断这个问题的"，干完之后把新发现写回去。知识在你手里（本地文件），不锁在任何一个 Agent 里。

---

## 一、它让你得到什么？

### 1. 持续积累的知识，而不是一次性的聊天记录

你给 Agent 一份文档、一个链接、一段讨论。Agent 不是简单存起来，而是：

- 提取里面的**实体**（一个产品、一个框架、一个人）、**概念**（一种设计模式、一种技术架构）、**判断**（A 比 B 更适合 X 场景，因为 Y）
- 把它们写成互相链接的知识页，注明每条知识来自哪份原始资料
- 新资料进来时，**更新已有页面**而不是另起一个重复的——你搜"工具管线"只看到一个页面，看到的结论来自多份资料的综合

比如，本对话中 DeepSeek Harness Wiki 的 `dsh-vs-other-frameworks.md` 起始引用了 2 篇中文分析文章，后来加入了 8 篇 Cordis 官方教程和 1 篇英文评论——三次更新都在同一个文件里，对比表从 3 个框架扩展到 6 个。

### 2. 有证据的回答

你问 Agent "这事我们怎么看的"，它不凭记忆回答。它先去知识库做**本地 BM25 关键词检索**，找到相关页面，读原文，然后告诉你——**同时告诉你结论的依据是什么**。

比如你问"DSH 的安全模型怎么样"，它会读 `tool-pipeline.md`、`dsh-vs-other-frameworks.md`、`session-log.md`，然后回答："fail-closed 审批 + Monotonic Guard 是区别于 Claude Code 按风险评级模型的关键差异，来源于这篇分析文章和那篇官方文档。"

### 3. 认识的变化轨迹——不只是"结论变了"，是"为什么变了"

当你加入新资料后，Agent 不只是更新页面。它还会：

- **拍快照**：更新前先保存旧页面
- **语义比较**：新证据和老结论到底差在哪——是事实错误被修正？（`update`）是两个来源在相同条件下得出矛盾结论？（`conflict`）还是不同版本不同条件下各自的合理判断？（`context_difference`）
- **生成认知简报**：把变化的原因、影响、证据整理好，等你确认

比如本对话中 Caspar Bannink 的文章加入后，生成的三条认知记录是：

> ① Claude Code 的扩展性描述从"预定义扩展点"修正为"Skills + 子 Agent + Hooks + MCP + 插件"（事实修正）
> ② 独立研究：同一模型只改进 Harness，Terminal-Bench 2 从 69.7% 升到 77.0%（新证据强化已有主张）
> ③ 极端模块化 = 无偿平台工程劳动（新论据丰富已有争议）

### 4. 健康检查——知识库现在有什么毛病？

- 哪些源文件还没被引用，可能漏掉了重要信息？
- 哪些页面是孤儿（没人链接），说明知识没接起来？
- 哪些链接指向不存在的页面，说明还有很多东西没写？
- 哪些原始文件被改过或丢了，证据链断了？

这些都是 `status` 和 `coverage` 操作一次性告诉你的。

### 5. 定时认知简报——每天早上推送"昨晚想明白的事"

你可以让 Agent 每个工作日早上 9 点做一件事：对比知识库的新旧状态，找到发生变化的认知，推给你。

简报不是"今天加了 3 个页面"那种数量报告——它只推**会改变你判断的变化**。

## 二、它不是什么？

- **不是聊天记录存档**——不会自动保存你和 Agent 的每一句话。只有你明确要求整理的内容才会进入知识库。
- **不是全自动的知识图谱构建**——Agent 做语义判断和综合，Python 辅助脚本做文件操作、哈希、图计算。没有 LLM 的推理，脚本不会自己"看懂"源文件。
- **不是向量数据库**——本地 BM25 关键词检索，不需要 embedding 模型或向量服务。
- **不是数据库或 SaaS**——所有知识存在本地 Markdown 文件里，可以用 Obsidian 或任何文本编辑器打开。Python 辅助脚本不联网。

---

## 三、它和 RAG 知识库有什么本质区别？

很多人听到"知识库"就想到 RAG——把文档切块，embedding 存向量库，用户提问时检索相似块塞进 Prompt。LLM Wiki 走的是另一条路。

### 根本差异：存入什么，取出什么

| | RAG 知识库 | LLM Wiki |
|---|---|---|
| **存入什么** | 原始文档的切片（chunk），加上 embedding 向量 | 经过 Agent 语义综合的**知识页**，互相链接 |
| **存入时做了多少加工** | 几乎没有——切完就存 | 大量——提取实体、概念、判断、关系，写成结构化页面 |
| **取出什么** | 与问题"长得像"的原始片段 | 被 Agent 综合过的、标明出处的**结论** |
| **搜索方式** | 语义相似度（向量近似） | 关键词（BM25）+ Agent 阅读后语义排序 |
| **更新时会发生什么** | 新文档 = 更多切片，旧切片和新切片混在一起 | 新证据修改已有页面，旧状态存快照，新旧一起审查 |

### 用一个例子说清楚

你加了 5 篇关于 DeepSeek Harness 的中英文文章进两个系统，然后问："DSH 的安全模型和其他框架比怎么样？"

**RAG 的做法**：

1. 把你的问题 embedding 成向量
2. 在 5 篇文章的几百个切片里找到 top-K 个语义相近的
3. 把它们塞进 Prompt，让模型现读现总结
4. 每次问、每次重新找、每次重新总结

结果：这次拿到的 top-K 和上次不完全一样，总结出来的东西每次都有细微差异。没有"这个东西我们已经确认了"的概念。

**LLM Wiki 的做法**：

1. **入库存的时候**，Agent 就读完了 5 篇文章
2. 提取出"工具管线"这个核心概念，写了一页 `concepts/tool-pipeline.md`，里面写着"fail-closed 审批 + Monotonic Guard + 先记调用再执行"
3. 又写了一页 `comparisons/dsh-vs-other-frameworks.md`，对比表中明确写着 DSH 的 fail-closed 区别于 Claude Code 的按风险评级
4. 你问的时候，Agent 搜"安全模型"，命中这两页，**直接读已经综合好的结论**，告诉你的同时给出两页中的原始引用

结果：每次问、同一个答案、同一套引用。因为加工发生在入库时，不在提问时。

### 更关键的区别：RAG 不会告诉你"我们以前判断错了"

这是 LLM Wiki 和 RAG 最深层的差异。

当你加了一篇新文章（比如 Caspar Bannink 的评论），RAG 只是多了一批切片。下次搜索"Claude Code 扩展性"时，运气好会同时抽出旧切片（"Claude Agent SDK 提供预定义扩展点"）和新切片（"Claude Code now supports skills, custom subagents, hooks…"）——然后模型在 Prompt 里临时判断"哦，这俩说的不太一样"。

LLM Wiki 呢？**它有一个完整的认知追踪流程**：

1. 更新 `dsh-vs-other-frameworks.md` 之前，给旧页面拍快照
2. 更新之后，`sync` 发现 4 个页面变了，生成一个审查批次
3. Agent 对比新旧版本，发现一个事实修正（Claude Code 不只是"预定义扩展点"）、一个新证据（Terminal-Bench 2 +7.3%）、一个新论据（unpaid platform engineering）
4. 存入三条认知记录，每条附着旧引用、新证据、影响和待确认问题
5. 推简报给你："这三件事值得你看"

RAG 不会做以上任何一件事。它不区分"新信息"和"已有信息"，不知道"这个新切片和旧切片在说同一件事"，更不可能记录"你的认知在什么时间、因为什么证据、从什么结论变成了什么结论"。

### 各自的适用场景

| | RAG | LLM Wiki |
|---|---|---|
| **适合** | 海量文档、快速检索、临时参考、客服 FAQ | 长期研究、需要综合判断、重视可追溯性、多 Agent 协作 |
| **不适合** | 需要稳定结论、需要知道"什么时候因为什么改了判断" | 一次性的文档检索、不需要反复使用的临时信息 |
| **加工成本** | 几乎没有（自动化） | 较高（Agent 在入库时做语义综合） |
| **检索成本** | 低（向量近似，毫秒级） | 中等（BM25关键词 + Agent 阅读） |
| **结论稳定性** | 不稳定（每次检索结果不同，每次模型临时总结） | 稳定（结论写死在页面里，有快照可回溯） |

### 它们不是替代关系

RAG 和 LLM Wiki 解决的是不同层次的问题。RAG 帮你**找到**可能相关的东西；LLM Wiki 帮你**记住已经确认的东西**。

实操中常见的组合：用 RAG 做初筛（"这 500 篇论文里有哪些可能和我的课题有关"），用 LLM Wiki 做沉淀（"读完这 5 篇，我确认了以下三个结论，它们和上次的结论一致/矛盾"）。

## 四、开始用之前需要什么

1. **一个支持 Agent Skills 的 AI Agent**：Codex、Claude Code、Hermes、Pi 都可以。需要能读写本地文件、能运行 Python 3.11+。
2. **Python 3.11+**：只是标准库，不需要 pip install 任何东西。
3. **如果处理网页/PDF**：需要 Agent 提供网页抓取工具。PDF 需要 Agent 能做文本提取（如 `pdftotext`）。
4. **如果定时推送**：需要 Agent 所在环境有调度器（cron、launchd 或 Codex/Claude Code 自带的任务系统）。

## 五、怎么用（三句话上手）

### 第一步：建库

告诉 Agent 知识库放哪里、积累什么：

> 用 llm-wiki 在 `~/my-wiki` 建一个知识库，积累 AI Agent 架构和评测相关研究，重点关注插件系统、安全模型和效果评估。内容用中文。

Agent 会和你确认目的、关注主题、语言，必要时补问缺失信息，然后创建初始结构。

### 第二步：加资料

> 把这个文件夹整理进知识库。

或者：

> 这篇文章会改变我们对 XXX 的已有判断吗？

Agent 会保存原始文件，提取知识，更新相关页面，对比新旧结论。

### 第三步：问问题

> 我们之前对 XXX 有哪些结论？有哪些不确定的地方？

Agent 会搜索知识库，找到相关页面，告诉你结论和来源。不是凭记忆回答。

## 七、知识库里面有什么

```
my-wiki/
├── wiki-purpose.md              # 目的、受众、关注主题、优先级
├── wiki-schema.md               # 页面类型和写作规范
├── wiki-agent.md                # Agent 在这个库的行为规则
├── wiki-log.md                  # 操作日志（每次改了什么）
├── wiki/
│   ├── index.md                 # 所有页面的目录
│   ├── raw/                     # 源文件的 Markdown 阅读副本
│   ├── entities/                # 实体页（产品、框架、人物）
│   ├── concepts/                # 概念页（架构模式、核心机制）
│   ├── findings/                # 发现页（评测结果、争议分析）
│   ├── methods/                 # 方法页（可重复使用的操作指南）
│   └── comparisons/             # 对比页（框架/方案对比）
├── sources/YYYY-MM-DD/          # 原始文件（只读、不可改）
└── .llm-wiki/                   # 内部状态（哈希、快照、审查）
```

## 八、扩展：不只是 Wiki，也可以是你的第二大脑

LLM Wiki 在安装时会把五个子技能也装进知识库：

- **ingest**：把资料变成知识（上面的"加资料"就是它）
- **query**：搜索并回答问题（"我们以前怎么判断"就是它）
- **lint**：健康检查（孤页、失效链接、薄弱证据）
- **research**：主动调研 + 覆盖空白（"这个方向我们还缺什么"）
- **briefing**：认知更新推送（"每天早上推我"）

装上之后，你可以跨不同的 Agent 用同一个知识库——今天用 Claude Code 加资料、明天用 Codex 查问题、后天让 Pi 推简报。知识在你手里，不跟着 Agent 跑。

## 九、和 Obsidian 的配合

`wiki/` 和 `sources/` 都是标准 Markdown 文件，页面之间用 `[[wikilinks]]` 互相链接。**你可以在 Obsidian 里直接打开这个目录当做一个 Vault**——用 Graph View 看知识结构，用 Backlinks 看哪些页面引用了某个概念，用搜索找东西。

Agent 读写了什么，你在 Obsidian 里都能看到、编辑、扩展。这是一套你和 Agent 共用的知识系统。
